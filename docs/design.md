# Design

## Decision 1: an obstacle is a pure function of the tick

mg-smash-copter's platforms are a spring the server integrates and replicates, because what they do depends on who stands on them. Nothing here does. An arm turns at a speed, a mover eases with a period, a tile drops on a schedule hashed from its index, so **where every obstacle is at tick N is a formula both ends evaluate, and nothing about the course is replicated after the document arrives**. A client predicting its own player poses the course at the tick it is simulating, first (`WoController._on_pre_simulate`, which runs during prediction replays too), so a jump over a sweeping arm lands or fails identically on both ends. `headless_net`'s "every obstacle is where the server has it" asserts it from both ends.

**Hazards are not solid to a player; carriers are.** A swept capsule meeting a body that moved into it between ticks is resolved by depenetration, which is order-dependent and differs between machines. So spinners, pendulums and pushers are measured analytically against the player's capsule (`WoCourse.knock`: segment–segment for an arm, point–segment for a ball, sampled box for a ram) and throw at the surface's own speed, clamped to `knock_min_speed`..`knock_max_speed`, plus `knock_lift`. Movers, turntables, rollers, seesaws, belts and tiles are solid, and whoever stands on one is moved by `WoCourse.carry`: the exact displacement `pose(t+dt)·pose(t)⁻¹·p − p`, not velocity times step, or a player standing still on a turntable spirals off it.

**Moving pieces are STATIC bodies, teleported, never `AnimatableBody3D`.** Godot's physics server applies a new transform to a kinematic body only at its next step (the first lands at once, later ones wait), so a client replaying six predicted ticks in one frame would sweep all six against obstacles a frame old. A static body's transform, written through `PhysicsServer3D.body_set_state` as well as the node (`WoCourse._place`), applies immediately. A frame posed between ticks (`pose_at_time`, client drawing) forgets its cached tick so the next `pose_at(N)` re-poses.

Everything derived from the tick follows the same rule and never goes on the wire:

- **Tells**: a drop-tile is red for `WoCourse.TILE_WARN_SECONDS` (0.6 s) before it drops (`tile_warning`). A `high_sweeper`'s arms pass above a crouch and below a standing head. A fall drips for `FALL_WARN_SECONDS` (0.7 s) before it pours (`fall_warning`).
- **Falls** (`fall`): a curtain of water, or slime by `tint`, across the way. It pours for `duty` of every `period` (`fall_on`) and throws whoever is under it off the side it pours toward (`push` along its own +X); measured like every hazard (`_knock_fall`), so a stand-in's `path_clear` waits for it. The sheet falling from the sluice and clearing from the top (`fall_sheet`) is drawing only.
- **Weather** is drawn once per round into the course document (`WoGame.draw_weather` into `doc["weather"]`): gusts (`wind_chance`, `wind_strength`) and lightning at drawn spots and ticks (`storm_chance`, `storm_strikes`, `strike_radius`, `strike_damage`) are pure functions of the tick in `WoCourse.wind` / `strike`, applied in the player's own predicted tick.
- **The machinery is heard** on the client, once a frame (`WoAudio.present_machinery(course, seconds, listener)`): an arm crossing the listener's bearing from its hub is a whoosh, a hammer through the bottom of its swing a whoosh, a ram at full reach a thump, a tile's warning a rattle. A jump in time (more than 0.25 s, or a new stage via `reset_machinery`) only remembers the time, or every arm would be heard at once. Which side of the bearing is a bool, not `signf` (`signf(0)` matches neither side). The listener must be set before the audio manager culls by distance. The sounds are synthesised into dot-audio's bank under the id and path a file would have, so an `.ogg` still wins.

## Decision 2: the course travels, whole

A course is a JSON document (`WoCourseDoc`); the server reads documents from `courses/` and sends the **normalised** one in `STAGE` (deflated, both lengths in a header, refused rather than decompressed when torn). A client needs no course files and cannot disagree about where a deck is. The client validates what it receives, so a client a format behind refuses with a sentence. `headless_net` checks the client's course digest equals the server's.

- **The document validator turns every weather number into a float**: JSON has one number type, and an int tick came back as a float and broke "the same document, to the byte".
- **The warmup's course is round one's.** `_ready` lays a course out (a world is never empty), `start()` rebuilds the same one (on a server the bridge exists only by then, so this is the build clients are sent), and the first round keeps it (`_course_unplayed`); later rounds draw the next, seeded, never the same twice running. `start()` rebuilds the warmup course only if the catalogue still offers it. `WoClient._on_stage` introduces a stage at most once per five seconds, because both rebuilds announced it.

## Courses that turn, climb and fork

A course is not a corridor: mg-wipeout-maps' builder turns, curves, climbs and splits it, and every piece, checkpoint and the finish carry a `yaw`, which every piece kind already read. Nothing in the game assumes a course runs down −Z; the overview camera fits the course's bounds and the race shot looks the way the runner faces.

- **A fork is format 2.** The route stays one list: a fork's branches are laid out after the point it starts at, each branch's points carrying its `branch` number and the faster one `risky`. `WoCourse.route_next(index, branch)` skips the other branch's points, `route_prev` walks back the same way, and `route_branches(index)` says what a fork offers. A format-1 build would send a stand-in down both branches one after the other, so a forked course says 2 and an older build refuses it with a sentence; every other course stays format 1 and plays on both.
- **The race order is by distance**, a fork counted at its shortest branch (`route_progress`), because by index a runner on the second branch would always lead one on the first.
- **No checkpoint inside a branch**: the other branch never crosses it. Checkpoints are crossed by number, so a branch only needs the trunk's.
- **A leg over or beside another** is refused by the builder (`_check_shape`), and a stand-in that does end up on an earlier leg below starts again from the nearest point there.

## Decision 3: a round is decided by the game, not by dot-match

`WoRules` returns CUSTOM when `WoGame` has decided, with the winner it decided; its only clock is a backstop (`countdown + course + handover + finale + 60 s`), so a round the game never decided still ends and dot-match does not warn at boot. **Solo is the default**: each player is a side of their own, numbered from `SOLO_SIDE_BASE` (100), so `team_of` gives dot-combat distinct sides (friendly fire is off, and everybody on side 0 would be team-mates). Sides are varints on the wire.

Course closed → `finishing_sides()`: two or more → handover into a drawn arena (spawn areas shuffled per round, positions drawn inside them, props and weapons drawn across the drop areas, non-finishers into the gallery, everybody invulnerable for `handover_seconds`); one → that side; none → the furthest checkpoint (`progress_decides`), else a draw. Final death: the last side with anybody up and not watching; on the clock, most people up, else a draw.

## The course vote

A round here is a course, so the players vote for the next one over dot-vote (`game/wo_vote.gd`, a `DotVoteDirector` over a `DotVoteListSource` of the playable courses, never the arenas). dot-vote's ROUND_END trigger opens a ballot at a round's end and applies it at the next, one course late; `WoVote` uses MANUAL instead: a ballot opens `wo_vote_after` (20) seconds into every course and is applied at the round's end (`apply: END_OF_ROUND`), setting `WoGame.next_course_id`, which the next `_lay_out_course` uses once (and drops if a `wo_reload` took the course away). The module advances the director once a server tick (`self_advance` off, `round_based` on) and calls `note_round_end` from `DotMatch.round_ended`; a final death's arena is the same round, so its `world_rebuilt` does not start the director over.

- **Rock the vote opens the ballot in the game, not in dot-vote.** Under MANUAL the director hands every opening to its host, a passed rock-the-vote included: without `WoVote`'s handler on `director.clock.expired` (reason `rtv`), `!rtv` answered "Rocked. 1 of 1." and nothing opened. A rocked vote still waits for the round's end (`rtv_apply`): changing the course mid-round drops everybody on it in the water. `rtv_delay_sec` is 0, because dot-vote's two minutes are longer than most courses and would make `!rtv` a command that never works.
- **The list is refreshed after the delivered courses arrive**, in `_game_load` as well as after `wo_reload`. Built before them, it held only the built-in practice course, and a list of one never opens a ballot.
- No time limit (`duration_sec` 0), the current course is on the ballot, no cooldown in plays (a server with two courses would otherwise offer nothing). Stand-ins do not vote, so a server of stand-ins never opens one.
- dot-vote's commands (`vote`, `rtv`, `nominate`, …) are the module's, so `!vote 2` in chat reaches them through `_on_chat_command` as the player who typed it. Voters are the bare session id, the spelling `voters_fn` lists.
- The client shell draws the ballot from the `map_ballot` notice (`DotVoteBallotFeed` → `DotBallotPanel` down the right-hand side); nothing of it is in this game's client. `tools/shot.sh --view=third --ballot` draws the same panel from this game's own vote, to look at.
- An owner reshapes it in `user://cfg/wipeout_vote.json` or `game.yml`'s `metadata: course_vote:`, keyed as `DotVoteRules`; `{"enabled": false}` leaves the rotation alone.

`examples/dedicated`'s "the course vote" section drives it through the console as a player's chat would: a nomination, the ballot opening on its own clock with the nomination on it, a vote by number, the round's end laying the winner, and rock-the-vote opening the next one early. Not yet tried in a browser.

**`maps.yml` (`cfg/server/addons/dot_map/` of the `--config` directory; the game ships none, and `cfg/` here is a link into mg-wipeout-maps, so a game-tier `cfg/game/mg-wipeout/dot_map/` file has no home in this repository) says which courses rotate** (dot-map's `DotMapRotationFile`, looked for in the `--config` directory; `sv_map_rotation_file` names it, `wo_maps_reload` re-reads it, `wo_rotation <name>` switches). `WoCatalogue` holds documents, not `DotMapDef`s, so it keeps a mirror of the ids for the file to mark `in_rotation` on. `rotating()` (the draw, the ballot, nominations) honours the mark; `playable_courses()` does not, so the map menu still loads a course the file leaves out, and marks it "not in rotation". A rotation in the file replaces `shuffle_courses`; `commands:` renames dot-vote's roles and `wo_courses`, `wo_reload`. With no file nothing changes. Subscribed pack courses (solo) are matched by id only. `dedicated` section "rotation file".

## Courses per round, hard landings and the flung knockout

A round runs `courses_per_round` courses before its final death, but only while two or more sides finish each: one finisher or none ends the round at once, as before. Between courses everybody is placed on the next start pad and healed, and points are kept. Health on the course can be switched off (`health_enabled`; the final death's fight keeps its health). A landing past `fall_safe_height` costs `fall_damage_per_metre` a metre, on top of a knock's cost per m/s thrown. The lower the health a blow finds, the wilder the knockout: at or below `knockout_fling_below` of full health the body takes the `wipeout_fling` ragdoll reaction, whose push is written into the death's damage (the field that already travels) so no wire change is needed.

## Damage on the course

A knock costs health by how hard it threw you (`knock_damage_per_speed`, 1.0: a slow arm 8, the hardest throw 22; at 1.4 a stand-in was out before its first checkpoint), charged on the authority when it notices the knock, since the throw is predicted, and **at most once a second** per player (`knock_hurt_tick`, cleared by `place_at`): a ram holding somebody against its stop re-throws them every few ticks and killed a pinned stand-in in a second. **A fall heals** as well as a checkpoint does (`checkpoint_heals`): the knock that threw you in already cost the time back, and on the longer courses the health added up over a dozen restarts until a field of eight was knocked out of the round on every hammer course. **Health that runs out on the course ends the round for that player** (`course_deaths_eliminate`): alive again at once, watching from the lounge, and `_course_is_over` counts them as off the course or a round with an elimination would always run its clock. Off, it is a restart from the last checkpoint. A checkpoint heals (`checkpoint_heals`). A death breaks the figure on the client (dot-player-char's `DotPlayerBodyBreak`), seeded from the player so every client agrees, mended 1.2 s later.

## The final death

- **Props are carried with dot-props' `DotGravGun`, one per player, server-side only.** The grab key rides in this game's own `WoNetCommand` (`grab`), because `DotFpsCommand`'s three spare buttons are fire, alt-fire and reload; the server turns the held state into an edge. Fire while carrying throws (`throw_impulse`). A thrown prop hurts by momentum (`throw_damage_per_impulse`) for three seconds, once per prop per 20 ticks, credited to the thrower.
- **A carrier is drawn carrying**: `WoPlayerNet.net_carrying` is one bit (the gun runs only on the server), `WoPlayer.is_carrying()` asks the gun where it runs and the bit where it mirrors, and `WoFigure` raises both arms.
- **Weapons are found**: pickups on the floor (`PICKUP`/`PICKUP_GONE` events), taken by standing on them, which builds a `ZeeWeaponRig` the first time (`WoGame.arm`). The client draws each as zee's world model, spinning, with a light under it. Watchers see the weapon in the figure's hand (`WoFigure`, from mg-smash-copter), read off the rig for a simulated player and off `WoPlayer.dealt` for a mirrored one.

## Toys

dot-props' toy catalogue (its [docs/toys.md](../../dot-props/docs/toys.md)), loose ones only, by the family's rule for a competitive game: a ball, a pin, a barrel or a tyre is on the `toy` layer, which no person collides with, so a runner walks through one and `WoGame._advance_toys` pushes it ahead of them, a little faster than they walk, and nobody loses a step to it (`headless_run` measures the runner's speed through the ball). A pad, a trampoline or anything solid would be a way past an obstacle or a step in a fight: `WoCourse._build_toys` leaves out any other kind with a WARN, on both ends alike, so the indexes still pair. A stage document's `toys` are validated in `WoCourseDoc` (an unknown id is left out and listed, never refused).

- **Where**: two beach balls in the start pen's back corners on every course (mg-wipeout-maps' `START_PEN_TOYS`), to bat about while the gate is up; and a beach ball and a football on the floor of four of the five arenas, clear of spawns and drops. The turning floor has none: it is moved by writing its transform, which carries a person (the carry) but not a rigid body, and a ball sat still while the floor turned under it.
- **In the finale** a shot pushes the first toy down its ray (`_shoot_toys`, dot-props' `shot_along`) and goes on to the combat, whose trace is the `world` layer alone, so a ball is never cover; a barrel's blast throws them (`TOY_BLAST_SPEED`). A ball in the water goes home (`kill_y` a metre under it), and every stage build puts them all home. `shot_along` is dot-props API 6, so a release of this game wants a shell with dot-props 6 in it.
- **On the wire**: `WoToyNet` replicates each toy's pose, `on` and use count; never predicted. TOYS (after STAGE, and to a joiner after theirs) carries the net ids in toy order and the stage's id. **A client registers every mirror the moment TOYS arrives** and pairs them with its own toys when that stage is built here, because dot-net stops reading a snapshot at the first entity a client does not know: a client without the stage would otherwise read no snapshot to its end (`headless_net`, armed). A released toy entity leaves the tree at once as well as the registry.
- `sv_toys*` are bound in the module, REPLICATED, and followed by the client; the toys' sounds are dot-props' stock (`WoAudio.on_toy`).

## Colour and light

The family's sunny look (game-arena's built-in maps) with this game's water and obstacles kept as they were: the obstacles are the only saturated things on screen.

- **Surfaces** are roles (`WoTextures`): the deck, supports, safe ground and the arena floor all draw Kenney's light grid tinted a pastel (`INSTALLED_TINTS`: a hair-under-white deck, mid-lavender supports, mint safe ground, lavender arena); only what moves (Kenney's orange) and what throws you (Kenney's red) keep a colour tile of their own. A pure-white deck clipped under the sun and lost the grid, which is how far a jump is; charcoal supports were black posts in a sunny frame.
- **Light is a dot-lighting document made from the course's theme** (`WoCourse.light_document`): the theme's sun colour, its sky at the zenith, its horizon as the fog from 120 m, its water darkened under the horizon; a warm high sun **behind the start**, so the faces a runner runs toward are lit (from the other side the orange start gate came out brown); a pale cool fill whatever the theme; filmic and glow. The theme is the course's identity (a lagoon, an overcast sea, a sunset) and stays in the course document; a repaint never touches geometry or the document's digest.
- **Compatibility** (this game's and the shell's renderer) clips a sunlit pastel to white at Forward+'s numbers, so `WoCourse.light_profile()` is dot-lighting's `painted()` (API 3), which matches its light to the renderer, lowers the exposure, grades and adds a shadowless fill. Shadows stay on in the browser. Check a look change in Forward+ too (`GODOT=<a wrapper that adds --rendering-method forward_plus> tools/shot.sh`).
- **A contact shade where still boxes meet** (`WoCourse._add_contact_shade`, dot-lighting's `DotContactShade`, API 4, by path behind `DotAddonApi.build_level`): soft bands where a block stands on a deck or a wall meets the pad, which SSAO gives on Forward+ and Compatibility cannot. Only the still `box` and `bouncer` pieces and the start pen's pad and walls: every other kind moves and the shade is one mesh built with the course, so it would stay where the piece was; ramps are tilted; the pen's gate drops. The pen's pad goes in as wide as the walls' outer faces, because the walls stand 5 cm off its edge and the pad as built meets none of them. Most decks float alone over the water, so a course has few creases (First Splash: 184 triangles). Rendered the Punch Alley pen and First Splash before and after.

## Cameras and bodies

The play test had stand-ins walking into the camera at the start line and the finish (a face filling the screen). Two server rules from dot-player-controller, bound REPLICATED by the module and followed by the client: `mp_solidplayers` (1) puts the player layer in every player's motor mask and gives each body a standing `SolidHull` (`WoGame._apply_body_mask`, again on every change), so a stand-in stops at your shoulder. Stand-ins are on a `bot` layer of their own: a person's mask has both layers, a stand-in's only the people's, so two stand-ins pass through each other (a solid field of eight pushed itself off every edge; [stand-ins](stand-ins.md#a-field-of-them)); `mp_forceview` (0) decides whether F5 may switch to third person (1 first only, 2 third only). The third-person camera is a dot-core `DotCameraBoom` swept from the eye with `CHASE_UP` added as `lift` (a pivot above the head can be inside a gantry), stopping against the course and props, never players. A `DotCameraFade` on the camera is handed every other player (`_other_players`), not found by a query, because the hulls are off when players pass through each other, which is when it matters. dot-spectate is handed the level for its chase and death cameras. `tools/camera_check.sh` flies both cameras round every piece of the course (armed) and runs a stand-in into a player's back with the rule on and off; `--render` draws both views and the walk-in before and after.

## The show

The play test: "make it seem like it's a huge event", and nothing round the course but sea. Everything here is client side and cosmetic; nothing of it is simulated or sent beyond the course document.

- **Dressing** (`dressing` in the document, [WoCourseDoc] `_dressing`): `stands` (a grandstand rising away from the course, with a crowd), `banner`, `lights` (a light tower), `screen` (a big screen) and `flags`. A kind this build does not know is dropped, never refused, so an older client still plays a newer course. Built only when `draw_world` (`WoCourse._build_dressing`); a server builds none of it. mg-wipeout-maps' `event()` dresses a whole course from its route.
- **The crowd** is three MultiMeshes over every stand (bodies, heads, arms) and one shader: each person bobs on their own phase, and with `excitement` they jump and put their arms up. `WoCourse.cheer(amount)` raises it, it falls back to `CALM` by itself, and a big cheer fires the confetti over the finish arch. Thousands of people are three draw calls.
- **The announcer** (`WoAnnouncer`) turns what the client already hears into a line under the course name (`WoHud.announce`, an accent line), a voice (Kenney's Voiceover Pack: three, two, one, go, hurry up, final round, winner, congratulations, time over, you win or lose) and the crowd (a gasp at a fall near the camera or by the leader, a cheer for a new leader or somebody home, a roar for the winner and the final death). Lines are rate-limited to one every 2.2 s unless they are about you, the leader or the winner. The big screens show LIVE, the clock and the first three (`screen_text`, every half second).
- **The sounds** are files in `audio/`, written by `tools/make_sounds.py`: the crowd (cheer, gasp, roar), the stadium horn and the water are synthesised there from fixed seeds (this repository's own); the voice lines are copied from Kenney's bundle (CC0). A file wins over dot-audio's synthesised stand-in, as everywhere in this game.

## The HUD

`wo_hud.gd` draws health and the clock through dot-ui's glance pieces: `DotScoreStrip` with the clock alone (hidden between rounds, red for the last ten seconds) and the phase line under it, the course name under that; `DotVitals` only in a final death, because nothing on a course can hurt you. Over the progress bar, the runner's place in the race ("3rd of 9", from `WoGame.race_order()`); under the course name, the announcer's line. Coloured by `WoHud.piece_theme()` (a violet-slate plate, the course name's amber as highlight). The health plate ends 206 pixels off the bottom, above the chat box's full eight-row log (202); the old number ended at 150, over the log, and only a full log showed it (`headless_run` checks the arithmetic). Naming these classes makes the pack need a client shell with dot-ui API level 4; the derived `requires.json` asks for it and `headless_run` checks that too.

## Points and the Tab board

`WoPlayer.points` add up over a match: `finish_points` by place (10, 7, 5, then `finish_points_rest` 3) and `winner_points` (10) for the round's winning side, on the authority. `net_points` and `net_ping` replicate; the module copies each session's dot-server `ping_ms` onto its player. Tab holds dot-menu's `DotMenuScoreboard` with this game's columns (avatar, name, points, place or "out", time, ping). The avatar is the figure's head rendered once per skin into a small SubViewport (`WoClient._portrait`), because every person is the same mesh and a few atlases cover every player.

## Delivery: the courses are a second pack

The game's pack does not contain `courses/` (a link, excluded in the pack). mg-wipeout-maps is published as its own pack and **`game.yml` does not name it**: a server owner names it in their deployment's map config (dot-server-deploy's `cfg/content.yml`, which fills `DotGameDescriptor.maps`), so which courses a server runs is the owner's choice, not a release of this game. Copying the documents into the game's pack loses: a new course would be a game release and a shell rebuild for every server.

`WoModule._add_delivered_courses` asks dot-game's `DotGameContent.map_dirs(server, "courses")` for every pack the server names (its maps, then any legacy `server_dependencies`) and adds each mount's `courses/` to the catalogue before `world.start()` and again after every `wo_reload` (which forgets everything). **`game.yml` sets `maps_delivery: client`**: the maps pack is also in every client's content sync, because an imported course's mesh (`worlds/`, about a megabyte each) is too large for STAGE; `WoWorld.prefix_of` finds it in any mounted `res://dot_cloud/*/*/worlds/`. `headless_net` "an imported course's mesh" is armed. A server with no maps pack plays `wo_practice` and logs it; dot-server-deploy's `examples/wipeout_client.tscn` exists to catch that.

## Spectators free-roam by default

Somebody knocked out of the final death may fly a free camera (G, `WoBindings.ROAM`). The game owns one `DotSpectatorRules` (`WoGame.spectate_rules`), shared with the manager; the module binds `mp_forcecamera`, `mp_freeroam` and `mp_freeroam_speed` on it (REPLICATED) and the client follows them. The key is an `Ask.ROAM` request the server decides (a refusal comes back as a notice), the existing `SPECTATE` event carries ROAMING back, and the client flies a `DotSpectatorFreeCam` per frame, so no camera position crosses the wire. `wo_spectate_camera` is an alias that writes through to `mp_forcecamera`, and a restricted camera wins over roaming silently.
